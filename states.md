# Estado Atual do Sistema

## Stack Tecnológica

- Java 17 com Spring Boot 4.1.0 e Maven Wrapper.
- Spring Cloud OpenFeign para integrações REST externas.
- Spring Web MVC para endpoints auxiliares de auditoria e quarentena.
- Spring Web Services, Jakarta XML Web Services API, JAX-WS RI e `jaxws-maven-plugin` para clientes SOAP da Vedacit/MultiTMS gerados a partir de WSDL.
- Spring Data JPA/Hibernate com Microsoft JDBC Driver para SQL Server.
- Banco SQL Server exclusivo `SATELITE_TMS_AUDITORIA`/`satelite_tms_auditoria` para auditoria, cursores e estado técnico da integração.
- Apache PDFBox e Java ImageIO/AWT para renderização, conversão, compressão e normalização de canhotos.
- WSDL/XSD da Vedacit empacotados em `src/main/resources/wsdl/vedacit` para criação de proxies SOAP dentro do Fat JAR.
- Lombok em entidades/modelos internos; testes com starters de teste Spring Boot para JPA, Web MVC e Web Services.
- Operação em Windows por `satelite.bat`, `build.bat` e scripts em `scripts/`; banco provisionado por `database/subir_database.bat`.

## Arquitetura e Padrões

- Aplicação middleware/ETL headless: o fluxo principal é acionado por Spring Scheduling em `OrquestradorEtlScheduler`, não por controller web.
- Arquitetura em camadas: `clients` concentra OpenFeign REST; `dto.rodogarcia` modela entrada ESL/Rodogarcia; `dto.ppg` modela saída PPG/OK Entrega; `services.etl`, `services.ppg`, `services.vedacit` concentram regras por domínio; `repositories` acessa auditoria SQL; `models` contém entidades JPA; `utils` guarda lógica pura de imagem/download.
- `SateliteApplication` habilita OpenFeign; `SchedulerConfig` habilita agendamento.
- `OrquestradorEtlService` coordena os destinos PPG, SELIA e Vedacit, respeitando toggles independentes, modo ciclo único e modo retroativo, e delega a cadência contínua de paginação/backoff para os serviços de fluxo e política ESL.
- O destino SELIA/Intelipost possui dois sentidos independentes: o receptor público de Pré Lista de Postagem (PLP) e o envio outbound AddEvents. `SELIA_INTELIPOST_PLP_ENABLED=true` mantém o receptor disponível; `APP_SELIA_ENABLED=true` já está preparado no `.env`, limitado pela whitelist e pendente apenas de recarga controlada do processo.
- O destino SUPPORTE é uma integração REST outbound pelo New Tracking, isolada em `clients/SupporteClient`, `dto.supporte` e `services.supporte/SupporteIntegrationService`. Ele usa Basic Auth configurado, DTOs `record`, cursor e auditoria próprios sob o identificador `SUPPORTE`, sem alterar os fluxos SELIA, PPG ou Vedacit; suas listas de configuração normalizam valores nulos de forma explícita para preservar a análise de nulidade.
- O guia operacional `docs/contexto/guia-postman-selia.md` documenta a PLP recebida, as consultas ESL, a validação do comprovante, o POST AddEvents controlado, as variáveis sem segredos, as dependências externas e os critérios de decisão por resposta HTTP.
- `docs/contexto/selia-homologacao-operacao.md` é o registro operacional definitivo da homologação SELIA/Intelipost, incluindo evidências, falhas corrigidas, variáveis e passagem segura para produção.
- `EtlFluxoDestinoService` encapsula paginação por destino, cursor, whitelists, filtro de ocorrência, detecção de loop de cursor, circuit breaker por falhas de infraestrutura, avanço seguro do cursor e pacing por lote de páginas; no incremental, um cursor persistido tem prioridade e não é combinado com `since`.
- `EtlRegistroService` aplica idempotência por log existente, processa pendências de canhoto, baixa comprovantes da ESL e atualiza o estado por registro.
- O reprocessamento manual de canhotos Vedacit usa exclusivamente os logs com `status_dados=SUCESSO`, `status_canhoto=ERRO_DESTINO` e `chave_cte` existente. Ele consulta o comprovante diretamente pelo CT-e, preserva o XML já confirmado e não depende da ocorrência histórica por `invoice_key`.
- `EtlRepescagemService` executa repescagem de erros definitivos do ciclo e repescagem ativa, sem janela de tempo, para falhas parciais de canhoto Vedacit com dados já integrados.
- A repescagem técnica Vedacit tem execução manual no menu `N` e agendamento diário da API às 23:30 BRT quando `APP_NIGHTLY_RETRY_ENABLED=true`. Ela seleciona no máximo 100 logs com até cinco tentativas e somente falhas técnicas de XML/CT-e ou canhoto (401, timeout, conexão e 429/5xx), atualiza o mesmo log de auditoria com o resultado e preserva fora da automação CT-e sem chave e recusas de negócio da Vedacit. Para erros históricos `401` cujo CT-e ficou apenas no URL da mensagem, extrai exclusivamente a chave de 44 dígitos, grava-a no mesmo log e reenvia somente o XML; o worker de Vedacit mantém esse agendamento desabilitado para não concorrer com a API.
- A auditoria de quarentena usa `dbo.tb_log_integracao_quarentena_evento`, vinculada ao log técnico sem duplicar XML, imagens ou dados de domínio. A entrada em quarentena é idempotente e cada tentativa posterior de repescagem registra resultado `SUCESSO`, `PENDENTE` ou `ERRO`, etapa, mensagem sanitizável e data. `GET /api/etl/quarentena/historico` pagina por período e destino, e `GET /api/etl/quarentena/historico/exportacao` transmite o CSV completo do período, sem teto de página. A migration V8 registra somente a entrada das quarentenas ainda abertas; tentativas históricas já sobrescritas antes dela não são inferidas artificialmente.
- `APP_ETL_REPESCAGEM_ENABLED` permite desligar a repescagem somente em ciclos isolados controlados, impedindo que uma validação SELIA reprocesse pendências históricas de outros destinos.
- `EtlEstadoIntegracaoService` centraliza status, tentativas, datas de processamento e conversão para resultado operacional.
- `AuditoriaDataHoraService` consulta o `SYSDATETIME()` do SQL Server para carimbar os registros de `tb_log_integracao`; se a consulta falhar, há fallback explícito para o fuso `America/Sao_Paulo`, sem modificar registros históricos.
- A retenção de logs de arquivo é executada pelo próprio processo Spring Boot online, independente do scheduler ETL: `LogFileRetentionService` verifica somente a pasta local `logs` a cada `APP_LOG_RETENTION_INTERVAL_MS`, mantém no máximo 20 arquivos pelos limites `LOG_RETENTION_MAX_FILES`, `LOG_RETENTION_MAX_AGE_DAYS` e `LOG_RETENTION_MAX_TOTAL_MB`, e remove também subpastas vazias. `scripts/rotacionar_logs.bat` permanece apenas como operação manual excepcional.
- `EtlResilienciaService` encapsula retries por erro transitório, backoff e limite de tentativas.
- `EslRequestPolicyService` impõe intervalo mínimo entre chamadas ESL, trata HTTP 429 com backoff bloqueante e retry transparente da mesma chamada, trata HTTP 5xx/falhas de transporte como transitórias e controla cooldown para consultas por período.
- A proposta de fonte SFTP complementar da Rodogarcia está documentada em `docs/blueprint/origem-sftp-rodogarcia.md`: SFTP será candidato somente para XML CT-e e comprovante/POD, com ESL preservada para ocorrências e fallback controlado. A conta compartilhada foi registrada exclusivamente no `.env`, permanece desabilitada e exige `SFTP_RODOGARCIA_CLIENT_PATH` explícito por cliente; o processo não poderá listar a raiz nem alternar subpastas. A automação usará cliente SFTP Java nativo com host key pinning, validação de arquivo estável e idempotência existente; FileZilla não participa do runtime.

- Regra Vedacit confirmada pelo gestor em 17/08/2026 para a reconciliação de canhotos SFTP: o CT-e indicado no nome do arquivo FTP é o CT-e efetivo do comprovante e prevalece quando houver mais de um CT-e de transporte para a mesma NF-e; para CT-e complementar, usar o CT-e de transporte indicado no FTP; para reentrega, usar o CT-e de reentrega indicado no FTP; para devolução, enviar o comprovante se ele existir no FTP, inclusive quando representar recusa anotada pelo destinatário. Após um único envio SOAP bem-sucedido, todos os CT-es comprovadamente relacionados àquela NF-e/canhoto devem ficar com status de canhoto `OK`, sem reenviar a imagem. A auditoria deve preservar o CT-e original da ocorrência, o CT-e efetivamente enviado e o vínculo/motivo de reconciliação; o histórico nunca pode ser sobrescrito. Não é permitido aceitar um arquivo somente pela NF-e, nem marcar CT-es sem relacionamento comprovado pelo XML/reconciliação. ## Regras de Negócio Consolidadas

- O fluxo principal só deve processar entrega realizada: `occurrence.code == 1`. Outros códigos são ignorados e auditados.
- Controllers não devem acionar o fluxo principal de integração; endpoints web existem apenas para auditoria, imagem de canhoto e quarentena/reprocessamento manual.
- Ações SQL manuais ou automatizadas devem atingir exclusivamente `SATELITE_TMS_AUDITORIA`; é proibido tocar `ETL_SISTEMA`, `DASHBOARDS` ou qualquer outra database.
- O banco guarda apenas auditoria, status, cursor e erros. Não persistir fisicamente NF completa, imagem de canhoto ou massa operacional de domínio.
- O cursor só avança depois do processamento/auditoria da página. Em erro de registro no modo incremental, o cursor não avança para permitir retry.
- O modo incremental usa `since` calculado como agora menos `ETL_INCREMENTAL_LOOKBACK_HOURS` (padrão 24 horas) somente quando não existe cursor persistido; com cursor, consulta somente `start`, mantendo paginação e avanço seguro sem a combinação incompatível da ESL.
- Em carga retroativa, erros por registro são registrados e a paginação pode avançar em memória para não travar o histórico.
- Em carga retroativa, `RETROACTIVE_MAX_PAGES`/`retroactive.max-pages` não podem ultrapassar `INTEGRATION_MAX_PAGES_PER_CYCLE`; o valor resultante define o tamanho do lote antes de pacing, não um limite terminal do ciclo.
- `INTEGRATION_MAX_PAGES_PER_CYCLE` não encerra mais a paginação; ao atingir o lote configurado, o fluxo pausa por `ETL_PAGINATION_PACING_PAUSE_MS` (padrão 30000 ms) e retoma do cursor em memória/persistido.
- Cada destino tem whitelists independentes de NF-e: `PPG_NFE_WHITELIST_ENABLED/PPG_NFE_WHITELIST` e `VEDACIT_NFE_WHITELIST_ENABLED/VEDACIT_NFE_WHITELIST`.
- Registros com status final `ENVIADO` ou `IGNORADO` não são reenviados automaticamente.
- Status consolidados atuais: `RECEBIDO`, `IGNORADO`, `ENVIADO`, `PARCIAL`, `PENDENTE_FOTO`, `PENDENTE_ORIGEM`, `ERRO_DESTINO`, `SUCESSO` e `NAO_APLICAVEL`.
- PPG exige canhoto disponível; sem imagem, o registro fica `PENDENTE_FOTO` e não envia payload.
- Vedacit pode concluir dados e canhoto separadamente; se canhoto faltar, o registro pode ficar parcial com `status_canhoto=PENDENTE_FOTO`.
- Quando a ESL responde sem XML de CT-e, o Satélite registra `status=PENDENTE_ORIGEM` e `status_dados=PENDENTE_ORIGEM`, preserva o canhoto, não incrementa tentativa nem entra na repescagem técnica. Uma nova emissão do mesmo CT-e é ignorada localmente até ação controlada após a origem disponibilizar o documento.
- Registros Vedacit com `status=ERRO_DESTINO`, `status_dados=SUCESSO`, `status_canhoto=ERRO_DESTINO` e `tentativas_canhoto < 3` são resgatados pela repescagem ativa sem limite de janela; o XML/dados é considerado já integrado e o retry executa somente download, compressão e envio SOAP do canhoto.
- Falhas parciais de canhoto preservam `status_dados=SUCESSO`, incrementam `tentativas_canhoto` a cada nova falha e entram na quarentena natural ao alcançar `tentativas_canhoto >= 3`.
- O dashboard de pendências deve exibir falhas parciais de canhoto ainda retryáveis como `Erro Parcial - Aguarda Retry`, evitando invisibilidade operacional.
- `QuarentenaService` seleciona a primeira mensagem disponível entre erro de dados, canhoto e erro geral diretamente pelos valores recebidos; não mantém sobrecarga local sem chamadas.
- O resumo analítico de integrações para o Dashboard deve agrupar no SQL Server por entidade operacional derivada de `tb_log_integracao`: `sistema_destino - XML/Dados` e `sistema_destino - Canhoto`. Como o banco de auditoria não persiste uma coluna física de tabela de negócio (`tabela_codigo`/`tabela_busca`), não se deve inventar essa dimensão no Dashboard nem agregar os logs em memória.
- Duplicidade retornada por PPG ou Vedacit é conciliada como sucesso, não como erro fatal.
- O runtime Vedacit não deve ler WSDL por caminho de filesystem como `src/main/resources`; a leitura deve ser por classpath (`getResource`) e falhar explicitamente se o WSDL local não estiver empacotado.
- Erros HTTP transitórios ou de infraestrutura incluem 500, 502, 503, 504, timeouts e falhas de transporte; há backoff e limite de tentativas antes de quarentena/bloqueio de retry automático.
- Circuit breaker de infraestrutura abre por falhas consecutivas conforme `ETL_CIRCUIT_BREAKER_TRANSIENT_FAILURE_THRESHOLD`.
- A ESL deve respeitar intervalo mínimo entre requests (`ESL_MIN_INTERVAL_BETWEEN_REQUESTS_MS`, padrão 2000 ms); HTTP 429 aplica backoff bloqueante (`ESL_TOO_MANY_REQUESTS_BACKOFF_MS`, padrão 120000 ms) e repete a mesma chamada no máximo por `ESL_TOO_MANY_REQUESTS_MAX_RETRIES` (padrão 2) novas tentativas. Ao esgotar esse limite, a falha transitória é auditada para reavaliação no próximo ciclo, sem teto mensal de consumo.
- Consultas por período usam cooldown: até 30 dias sem cooldown adicional, 31 a 183 dias com 1 hora, acima disso com 12 horas.
- Toda credencial, URL e token deve vir de `.env`, `application.properties` ou variável de ambiente; não pode haver segredo hardcoded.
